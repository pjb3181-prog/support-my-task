- 모델: `risubard-updates/tests/real_app/llm_stub.cjs`(OpenAI 호환 로컬 스텁, 포트 6200). `POST /ctl`로 시나리오(본문 길이, 비평가 응답, 에코 토큰 동작, 스트림 속도, 보조 호출 지연)를 바꾸고 모든 요청을 JSONL로 기록한다.
- 호출자 프로브: `tests/real_app/token_probe.js`(테스트 전용 플러그인). World Editor Lab `ai()`와 같은 형태(호출 토큰 + 결과 토큰 에코 요청)의 내부 호출을 한 번 보낸다. World Editor Lab 자체를 UI로 구동한 것은 아니다.

- 한계: 모델은 스텁이다. 문학적 품질, 실제 모델의 지시 순응도, 실사용 지연은 측정하지 못했다.

## 1. 실제 앱에서 새로 발견한 문제와 수정 (코드 변경 있음)
**문제: 스트리밍 응답에서 Bard Editor Lab과 Story Runner가 같은 본문을 둘 다 고친다 (영수증이 무력화됨).**
- 호스트는 채팅 출력 리스너를 플러그인 등록 순서대로 하나씩 실행한다(`pluginChatOutput.ts`). 플러그인은 동시에 시작되므로 등록 순서는 시작 속도에 따라 정해진다. 실제 앱에서는 Bard Editor Lab이 먼저 등록되었다(권한 팝업 순서·요청 순서로 확인).
- 결과: 스트림 종료 50ms 뒤 Bard가 진단+퇴고(2회)로 본문을 고쳐 저장했고, 그 뒤에야 Story Runner가 비평가를 호출했다. Story Runner가 받은 스냅샷은 Bard 수정 전 본문이라 재작성은 쓸모없어졌고(저장 보호로 덮어쓰기는 막힘), 영수증은 원본 서명으로 남아 의미가 없었다. 비용 중복이며 두 플러그인의 편집이 겹친다.
- 수정(플러그인만, 새 전역 상태·폴링 없음): Story Runner가 검수할 응답을 요청하는 시점(`beforeRequest`, 최고 품질·AI 모드·실행 중)에 같은 영수증 키에 `state:'pending'`을 적고, 검수가 끝나면 `reviewed`(영수증) 또는 `released`로 바꾼다. 검수 대상이 아닌 요청이 오면 남은 `pending`을 지운다. Bard Editor Lab은 신선한 `pending`(10분 이내)이 있으면 퇴고를 건너뛴다. 오래된 `pending`은 무시되므로 요청이 유실되어도 편집이 오래 막히지 않는다.
- 알려진 한계: Story Runner가 `pending`을 선언한 뒤 비평가 호출이 실패하면(JSON 아님 등) 그 응답은 Bard 퇴고도 받지 못한다(일반 응답 경로에서는 Bard가 이어서 퇴고함). 비평가 실패 시 원문 유지이므로 데이터 손실은 아니다.
- 모의 테스트 6개 추가(announce/release/clear/aux, Bard defer/expiry). 전체 204개 통과.

## 2. ① Bard Editor Lab 자체 퇴고 (실제 앱, 긴 본문)
| # | 조건 | 호출 순서 | 최종 저장 | Bard 기록 |
|---|---|---|---|---|
| T1(수정 전) | 스트리밍, Story Runner 최고 품질(비평가 OK) | 본문 → **Bard 진단·퇴고** → Story Runner 비평가 | Bard 퇴고본 | applied (영수증 무력) |
| T1b(수정 후) | 동일 | 본문 → Story Runner 비평가 | 원문 그대로 + 영수증 `reviewed` | skipped: 검수 완료 |
| T2 | 스트리밍, Story Runner 꺼짐(영수증 없음) | 본문 → Bard 진단·퇴고 | Bard 퇴고본 1회 교체(+82ms) | applied, 호출 2 |
| T3 | 비스트리밍, Story Runner 꺼짐 | 본문 → Bard 진단·퇴고(저장 전) | Bard 퇴고본 | applied(저장 전 편집), 호출 2, 저장 후 재퇴고 없음 |
| T4 | 비스트리밍, Story Runner 최고 품질 | 본문 → 비평가 → 재작성 | Story Runner 재작성본 + 영수증 | skipped: 검수 완료 |
- 메시지 손실·중복 없음: 모든 시나리오에서 메시지 수가 사용자 1 + 응답 1씩 증가했고, 최종 본문 길이가 영수증 서명과 일치했다. 이전 응답의 오래된 영수증(다른 본문)은 새 응답의 퇴고를 막지 않았다(T2).
- Bard의 장면 보조(`NEXT USER TURN DRAFT`) 호출이 응답마다 1회 추가로 발생한다. 퇴고와 별개의 기존 기능이다.

## 3. ② 내부 AI 호출 구분
**핵심 발견(실제 앱 + 소스):** 플러그인 API `risuai.runLLMModel`은 `requestChatDataMain`을 직접 호출하며, `beforeRequest`/`afterRequest` 대체기는 `requestChatData`에서만 실행된다(`request.ts:211`, `:292`; `v3.svelte.ts:1574`). 따라서 `runLLMModel` 기반 내부 호출(World Editor Lab, Bard Editor Lab, Story Runner의 비평가·재작성)은 다른 플러그인의 요청 훅을 거치지 않는다. 비평가 요청의 메시지 수가 항상 2개(훅의 시스템 메시지 주입 없음)로 기록된 것도 일치한다.
- 호출 토큰/에코 프로토콜은 이 호스트에서는 필요하지 않은 방어층이다(훅이 닿을 수 있는 다른 호스트 경로를 대비한 이중 안전장치). 제거하지 않았다(검증된 동작, 회귀 위험 없음). 다만 프롬프트에 에코 지시가 들어가는 비용이 있다.
- 실험(프로브, Story Runner 최고 품질 실행 중): 모델이 토큰을 정상 에코(follow) / 누락(drop) / 변형(mangle) 세 경우 모두 추가 요청 0건, 응답 변형 없음. 누락·변형에도 일반 후처리가 개입하지 않았다(훅 미적용이므로).
- 동시성: 일반 채팅(응답 6초 지연) 진행 중 내부 호출 2건(토큰 누락 모드)이 끝났다. 일반 응답은 도착 후 비평가→재작성→저장이 정상 수행되었고(Story Runner 재작성본 1건), 내부 응답은 영향받지 않았다. 일반 후처리가 생략되지 않았다.
- 결론: 본체(호스트) API 확장은 필요하지 않다. 전역 상태·폴링도 추가하지 않았다.
- 미확인: 훅이 `runLLMModel` 경로에도 적용되는 다른 호스트 버전에서의 동작(그 경우에도 토큰 프로토콜이 보호). World Editor Lab UI 자체를 통한 실행.

## 4. ③ 긴 스트리밍 (6,000자, 스텁 모델: 스트림 7.0초, 비평가 4.0초, 재작성 4.0초 지연)
- 스트림 종료(저장) → 재작성본 교체까지 **8.24초**(비평가 4.0 + 재작성 4.0 + 약 0.24초 오버헤드). 지연의 대부분은 비평가·재작성 모델 호출 시간이다.
- 메시지 교체 횟수 **1회**(원문 저장 → 재작성본). 중간 상태·이중 저장 없음. 영수증 `reviewed`, 서명이 최종 본문(6,009자)과 일치. Bard Editor Lab은 건너뜀.
- 화면 깜빡임: 교체가 한 번 일어나며 그 사이 사용자는 원문을 읽을 수 있다. 시각적 깜빡임 자체(렌더링)는 계측하지 못했고 DB 상태 전이만 확인했다.
- 일반 응답과 스트리밍 응답의 최종 저장 결과(T4 vs T1b/T3b): 둘 다 Story Runner 재작성본 + 영수증 `reviewed` + Bard 건너뜀으로 기능적으로 일치. 차이는 시점(일반: 저장 전 / 스트리밍: 저장 후 교체)뿐이다.
- 미확인: 재작성 중 사용자가 새 턴을 보내거나 편집할 때의 호스트 동작(리스너를 await하므로 채팅이 바쁜 상태로 유지된다는 소스 분석만 있음), 실제 모델의 지연.
