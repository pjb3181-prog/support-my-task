# 스트리밍·일반 응답 일관성과 내부 호출 동시성 (PR #42 후속, 2026-11-13)

근거: `RisuBard_modi1_private`(2c37be0) 소스 열람 + 플러그인 vm 모의 테스트. **실제 앱 실행으로 확인한 것은 없다**(7항 참고).

## 1. 호스트에서 확인한 호출 시점 (소스 기준)
| 단계 | 일반(비스트리밍) | 스트리밍 |
|---|---|---|
| `beforeRequest` 훅(`request.ts:211`) | 실행 | 실행 |
| `afterRequest` 훅(`request.ts:292`, 조건 `da.type === 'success'`) | **실행** | **실행 안 됨** |
| 메시지 저장 후 `editoutput` 스크립트 | 실행 | 스트림 종료 후(`index.svelte.ts` ~3075) |
| 커밋 후 `dispatchCommittedChatOutput` → `addRisuChatListener('output')` (`index.svelte.ts:3118`, `:3216`) | 실행 | 실행 |

- 출력 리스너는 **직렬화된 스냅샷**을 받고 `await`로 순차 호출된다(`pluginChatOutput.ts` `dispatch`). 리스너에서 채팅을 바꾸려면 `setChatToIndex`를 써야 하며, 리스너가 오래 걸리면 호스트가 기다린다(그래서 협업 모드는 `void`로 분리).
- 즉 스트리밍에서도 "커밋된 출력"은 리스너로 항상 받을 수 있다.

## 3. 이 브랜치에서 한 것 (스트리밍)
1. Story Runner `onChatOutput`: 커밋된 메시지에 표식이 있으면 `persistCleanedCommittedOutput`로 그 메시지 하나만 정리한다.
   - 메시지가 리스너가 본 내용과 **정확히 같을 때만** 쓴다(사용자 수정·다른 플러그인 수정·새 턴을 덮어쓰지 않음).
   - 이미 정리된 일반 응답은 `cleaned === content`라서 **다시 저장하지 않는다(이중 저장 없음)**. 멱등.
   - 완료 판정 분석은 정리 전 텍스트(`content`)를 계속 사용한다(폴백이 표식을 본다).
   - `setChatToIndex`는 일반 출력 이벤트를 다시 내지 않는다고 기존 코드가 가정한다(`story_runner.ts` 5369행 주석). 이 가정은 소스로 확인하지 못했다.
2. Bard Editor Lab: 자동 퇴고가 표식을 제거한 텍스트를 원문으로 삼고, 커밋 시 비교도 표식 제거 기준으로 한다. Story Runner가 먼저 정리하든 나중에 정리하든 퇴고가 "원문이 변경되어"로 버려지지 않는다.
3. 기존 일반 응답 경로(`afterRequest`)와 검수 영수증은 그대로 유지한다. 퇴고 중복 방지는 기존 영수증(`risubard_editorial_receipt_v1:<chatId>`)을 그대로 쓴다.

## 4. 아직 비어 있는 것: 스트리밍의 품질 재작성·불합격 처리
- 스트리밍은 이미 화면에 표시된 뒤라 `afterRequest`처럼 "저장 전에 대체/삭제"할 수 없다. 이 차이는 호스트 구조 때문이며 플러그인만으로 완전히 같게 만들 수 없다.
- 현재: 불합격은 기록(`flagRejectedStory`)되고 노트북·다음 자동 턴만 막는다. 불합격 본문은 채팅에 남는다.

## 5. 설계안 (구현 전, 승인 필요)
스트리밍 응답의 "저장 후 검수"를 일반 응답과 같은 기능으로 맞추는 방법:
- **A. 저장 후 재작성(플러그인만)**: 출력 리스너에서 품질 검사 → 필요 시 재작성 → 위 `persistCleanedCommittedOutput` 방식으로 *그 메시지 하나만* 교체(원문 불변 확인, 백업 기록). 영수증에 "Story Runner 검수 완료 + 서명"을 남겨 Editor Lab이 같은 원고를 다시 퇴고하지 않게 한다. 비용: 사용자가 원문을 잠깐 본 뒤 교체됨(깜빡임), 응답 후 지연. 리스너는 `void`로 분리해 호스트를 막지 않는다.
- **B. 호스트 확장**: 스트림 종료 직후·저장 직전에 `afterRequest`와 같은 시그니처의 훅을 한 번 더 호출. 일반/스트리밍 동작이 같아지지만 본체 수정이 필요하다.
- 권장: A(범위를 최고 품질 모드·불합격 처리로 한정) → 실제 사용에서 깜빡임이 문제면 B를 별도 PR로.
- 위험: 재작성 모델 호출 비용 증가, 사용자가 이미 읽은 문장 변경, 영수증 TTL(15분) 내 중복 방지 범위.

## 6. 내부 호출과 일반 채팅의 동시성
### 6.1 문제 (이전 구현)
`afterRequest`는 프롬프트를 볼 수 없어 요청 단위로 내부 호출을 구분할 수 없었다. 그래서 전역 레지스트리(`risubard_internal_call_v1`)로 "진행 중인 내부 호출이 있으면 우회"했고, 그 사이에 끝난 **일반 채팅 응답도 후처리를 건너뛰었다.**
### 6.2 현재 구현 (플러그인만, 전역 상태·폴링 없음)
- 요청: `[[RISUBARD_INTERNAL_CALL:<id>]]`를 프롬프트에 넣는다 → `beforeRequest`는 그 요청만 건너뛴다.
- 응답: 모델에게 답변 첫 줄에 `[[RISUBARD_INTERNAL_RESULT:<id>]]`를 쓰게 한다 → `afterRequest`는 그 토큰이 있는 응답만 건너뛰고, World Editor Lab이 토큰을 제거한 뒤 사용한다.
- 동시에 끝나는 일반 채팅 응답에는 토큰이 없으므로 **항상 정상 후처리**된다(테스트로 검증). 전역 상태·TTL·정리 코드가 모두 사라졌다.
- 한계: 모델이 에코 지시를 무시하면 그 응답은 일반 응답처럼 처리된다(채팅은 손상되지 않고, 내부 응답이 후처리를 받음 — Story Runner는 말미 표식 제거 정도이고 AI 실행 모드·최고 품질에서는 재작성/거부로 `''`가 되어 World Editor Lab이 "응답이 비어 있어"로 실패 → 재시도 가능). 모델 순응도는 실제 모델로 확인하지 못했다.

### 6.3 방식 비교
| | 레지스트리(이전) | 요청·응답 토큰(현재, 플러그인만) | 호스트 API 확장 |
|---|---|---|---|
| 요청 단위 구분(before) | 가능(토큰) | 가능 | 가능 |
| 응답 단위 구분(after) | **불가** → 동시 일반 응답 오인 | 가능(모델 에코에 의존) | **정확히 가능** |
| 전역 상태/폴링 | 있음(TTL·정리) | 없음 | 없음 |
| 본체 수정 | 불필요 | 불필요 | 필요(소규모) |
| 실패 시 | 일반 응답 후처리 누락 | 내부 응답이 일반 처리됨(드묾) | 없음 |
- 호스트 확장안: `runLLMModel`이 `requestChatDataMain`에 `origin:{plugin}`을 넘기고, 훅 호출을 `replacer(content, model, meta)`로 확장(기존 플러그인은 3번째 인자를 무시하므로 하위 호환). 변경 지점은 `v3.svelte.ts` `runLLMModel`, `request.ts` 훅 호출 2곳, 타입 정의 정도다. 본체 수정이 불가피하지 않아 **이번 PR에는 넣지 않았다.** 에코 순응도가 문제로 확인되면 별도 브랜치·PR로 진행한다.
- 검토했으나 채택하지 않은 방식: `mode:'otherAx'` + `staticModel`로 보조 모드처럼 보내기 → 훅이 자동 우회하지만 모델 프리셋 바인딩을 건너뛰고 보조 모델 샘플링 설정을 써서 사용자가 고른 "기본 모델" 동작과 달라진다.

## 7. 검증 범위
- 모의 테스트(실제 플러그인 파일을 vm에 로드, 호스트는 모의): 내부 호출 중 일반 응답 후처리, 토큰 에코 제거, 스트리밍 표식 정리, 이중 저장 방지, 변경된 메시지 보호, 편집기 표식 허용.
- **실제 앱 실행은 하지 않았다.** 격리 실행은 가능해 보인다: 서버가 `RISUBARD_DATA_ROOT`로 데이터 경로를 지정할 수 있다(`server/node/data-root.cjs`). 다만 (a) 플러그인 설치·캐릭터/채팅 생성을 UI로 해야 하고, (b) 스트리밍을 확인하려면 로컬 스트리밍 모델 스텁이 필요하며, (c) 설치 폴더 밖에서 서버를 띄우는 구성을 별도로 맞춰야 해서 이번 단계에서는 진행하지 않았다.
- 확인하지 못한 것: 실제 훅 등록 순서, 실제 스트리밍 중 리스너 호출 타이밍, 모델의 에코 지시 순응도, `setChatToIndex`가 출력 이벤트를 다시 내지 않는다는 가정.
